# 歷史文件追溯區

> 目的：保存自舊 `docs/` 匯入的歷史文件，供架構追溯、決策比對、舊規格盤點與 remediation 脈絡查核使用。  
> 這個目錄**不是正式開發文件區**，也**不是現況系統設計的權威來源**。

## 1. 定位

`SA/legacy-import/` 的角色只有三個：

- 保存舊 `docs/` 的歷史內容
- 提供正式 `SA/` 文件回寫時的追溯來源
- 讓人或 AI 在需要比對舊決策時，有固定可查的歷史區

以下內容都**不應**直接從這裡當成正式依據引用：

- 現況模組責任
- 現況 API 契約
- 現況資料模型定義
- 現況權限與 scope 規則
- 現況前後端互動方式

上述內容若仍有效，必須先回寫到正式 `SA/` 文件，再以正式文件為準。

---

## 2. 與正式文件的關係

正式文件權威入口一律是：

- `SA/README.md`
- `SA/architecture/`
- `SA/modules/`
- `SA/governance/`
- `SA/SDD_PROGRESS_TRACKER.md`
- `SA/CHANGELOG.md`

`SA/legacy-import/` 僅作為：

- 歷史藍圖來源
- 舊版規格快照
- remediation / audit / 工作票歷史脈絡
- 舊決策追溯材料

簡單說：

- `SA/` = 正式文件
- `SA/legacy-import/` = 歷史追溯

---

## 3. 使用原則

### 3.1 可以怎麼用

可以用於：

- 查舊版 SA2.1 / SA1.7 藍圖內容
- 確認歷史規格最初怎麼寫
- 比對現況設計與原始藍圖差異
- 追溯 remediation / audit / fix spec 的上下文

### 3.2 不可以怎麼用

不可以：

- 直接依 `SA/legacy-import/` 改程式
- 直接把舊 `docs/` 內容視為現況正確答案
- 略過正式 `SA/` 文件，只靠歷史文件做設計決策
- 把新決策、新 spec、新規則寫回 `legacy-import/`

---

## 4. 正確引用流程

若你在 `SA/legacy-import/` 看到一段仍可能有效的舊資訊，正確流程是：

1. 先比對現況程式碼與正式 `SA/` 文件
2. 判斷該資訊是否仍成立
3. 若仍成立，回寫到對應正式文件：
   - `SA/architecture/`
   - `SA/modules/`
   - `SA/governance/`
4. 若回寫完成，之後應引用正式文件，不再直接引用歷史檔

原則：**歷史內容要先被吸收成正式文件，才能重新成為開發依據。**

---

## 5. 來源

- 原始來源：`/opt/attendance-system/docs`
- 匯入策略：整體保留原始結構，避免歷史決策與脈絡遺失
- 現況角色：僅供追溯，不再作為正式文件區

---

## 6. 未來維護規則

1. 新開發一律只更新 `SA/`
2. 若需引用舊資訊，先比對程式現況與正式文件，再決定是否回寫
3. 不可再把新文件寫回舊 `docs/` 或 `SA/legacy-import/`
4. 若某批歷史文件已完全被正式文件吸收，才可討論是否刪除原始 `docs/`

---

## 7. 刪除舊 `docs/` 前的最低條件

在真正刪除原始 `docs/` 目錄前，至少應確認：

- 重要架構藍圖已在 `SA/` 有正式對應文件
- 模組責任與邊界已在 `SA/modules/` 或 `SA/architecture/` 收斂完成
- 治理規則已在 `SA/governance/` 固定下來
- 舊 `docs/` 中仍需保留的歷史材料，已搬入 `SA/legacy-import/`
- 不再有正式文件直接把舊 `docs/` 當作現況權威來源

---

## 8. 給未來 AI 的一句話

> 先讀正式 `SA/`，需要追溯歷史時再讀 `SA/legacy-import/`。不要把歷史文件直接當成現況設計文件。
