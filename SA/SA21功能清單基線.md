# SA21 功能清單基線

> 目的：以 **SA2.1 / 舊版藍圖** 為出發點，先整理出這套系統「應該有哪些功能」，再作為後續建立 SDD、拆解 SaaS 問題、以及對照現況開發成果的母表。  
> 這份文件**不是現況實作盤點**，而是偏向「原始設計基線 / 目標功能清單」。  
> 後續應搭配現況對照文件使用，而不是直接把現況當成這份文件的內容。

---

## 1. 這份文件的定位

你現在要走的順序是：

1. **先制定功能清單**
2. **再建立 SDD**
3. **再拆解 SaaS 需要注意的設計問題**
4. **最後才拿目前已開發功能來比較差距**

所以這份文件要回答的是：

- 這套系統在 SA2.1 規劃裡，本來應該有哪些功能
- 這些功能屬於系統級、平台級、SaaS 級，還是業務模組級
- 哪些功能是藍圖明確有，但現在未必已落地

這份文件**先不負責回答「現在有沒有做出來」**，而是先把「應該有什麼」定清楚。

## 3. SA2.1 核心設計前提

在拆功能前，先固定幾個 SA2.1 的母原則：

### 3.1 架構型態
- Platform-first Identity
- Same Database
- Same Tables
- Tenant Isolation via `company_id`

### 3.2 使用者與資料分離
- `users` 是 Platform User（全域身份）
- 業務資料是 Tenant Data（租戶資料）
- `company_id` 只存在於 Tenant Data / Membership Data

### 3.3 request context 原則
- 每次 request 必須建立 `current_user_id`
- 每次 request 必須建立 `current_company_id`
- `company_id` 不可信任 request body

### 3.4 company scope 驗證順序
1. Scope Validation
2. Tenant Isolation
3. Feature Gate
4. Location Policy（若流程需要）

### 3.5 跨模組限制
- 不可直接 import 他模組 service
- 不可直接 import 他模組 repo
- 不可跨模組直接寫表
- reporting 只讀

### 3.6 SA1.7 補充檢查結論
我回頭查到 `SA/legacy-import/docs/saold/SA_MODULE_SPECV1.7.md`，它確實是你原本的 1.7 版。

比對後結論是：
- **SA2.1 已經涵蓋大多數核心概念**，尤其是 Platform-first、Tenant Isolation、Feature Gate、Location Policy
- **但 SA1.7 還有一些偏工程實務的規則，SA2.1 沒有寫得那麼明白**
- 這些規則若不補回來，後面做 SDD 或現況比對時容易漏掉

因此本文件下面額外補了幾個來自 SA1.7 的重點：
- 單租戶備份 / 還原前置檢查
- tenant isolation 的工程保證手段
- API error handling 決策原則
- trusted device / site pairing
- attendance / leave / accrual / reporting / dispatch 的邊界語意
- 必跑測試類型
- 租戶資料模型設計原則（UUID / index / restore-friendly）

# 4. 系統級功能（System-Level Functions）

這一層不是單一模組功能，而是整個系統成立必須先有的能力。

## 4.1 多租戶架構（Multi-tenant Architecture）
- 同庫同表架構
- 以 `company_id` 做租戶隔離
- 所有 Tenant Data 都必須帶 `company_id`
- 所有 Tenant Data 查詢都必須受 `company_id` 限制

## 4.2 平台身份架構（Platform-first Identity）
- 使用者是全域身份(`super_admin`)，不直接屬於單一 company
- user 與 company 的關係透過 membership 建立
- request 內的 active company 是本次 scope，不是 user 永久唯一 company

## 4.3 資料分類（Data Classification）
- Platform Data
- Membership Data
- Tenant Data
- 不同資料類型有不同 isolation / restore / query 規則

## 4.4 request context 建立
- 解析身份
- 驗證 membership 或 assignment
- 建立 current company scope
- 禁止 request body 自帶 company 作為權威來源

## 4.5 模組化架構規範
- 每個模組需有 `api.py / service.py / repo.py / models.py / docs.md / tests/`
- 每個模組要有明確 responsibility / non-responsibility

## 4.6 跨模組互動規則
- 優先事件驅動（event-driven）
- 同步互動只允許 minimal public interface
- 禁止 service / repo 直接跨模組耦合

## 4.7 租戶安全的工程保證機制（來自 SA1.7 補充）
這是 SA1.7 很重要、但 SA2.1 沒明講完整的一點。

除了「規定查詢要帶 company_id」之外，系統還應考慮**工程層級的保證手段**：
- Repo Base / Query Helper：統一注入 tenant filter
- Middleware / dependency：統一建立 tenant context
- DB RLS（Row Level Security）：作為最後一道保命線

中文意思很簡單：

> 不能只靠工程師記得加 filter，最好要有系統級機制，讓漏寫也不容易跨租戶。

# 5. 平台級功能（Platform-Level Functions）

這一層是在講整個 SaaS 平台共用的治理與基礎能力。

## 5.1 身份與登入（Identity / Authentication）
- 使用者登入
- JWT token 發放
- JWT claims 設計
- per-company login uniqueness
- 平台身份與公司身份的對接

## 5.2 company scope 驗證（Scope Validation）
- 驗證 user 是否屬於 company
- 驗證 customer_service 是否有 assignment
- 驗證 super_admin 是否可全域操作
- 驗證公司內角色是否符合操作需求

## 5.3 角色模型（Role Model）
- `super_admin`
- `customer_service`
- `company_user`
- 公司內部角色需再細分（如 `company_admin` / `hr_manager` / `employee` 類型）

## 5.4 功能分級（Feature Flags / Entitlements）
- 公司是否可用某功能
- 以 entitlement / feature gate 管理 SaaS 功能差異
- API 執行時需做 feature gate 檢查
- feature key 需要可命名、可治理、可擴充

## 5.5 稽核與治理（Audit / Governance）
- 系統操作紀錄
- 查詢與匯出
- 保留政策
- 資料清理
- 高風險操作需可追溯

## 5.6 備份與還原（Backup / Restore）
- 單一公司備份
- 單一公司還原
- 租戶隔離不被破壞
- 還原不能污染其他 company

## 5.7 客服跨公司支援（Customer Service Scope）
- 客服可支援哪些公司
- 以 assignment 控制 scope
- 不等於一般 `company_admin`
- 高風險動作必須寫 audit log

## 5.8 API 錯誤處理策略（來自 SA1.7 補充）
SA1.7 有一段很實際，但 SA2.1 沒明寫完整：

- FastAPI / Pydantic schema 驗證錯誤 → `422`
- 系統層 business rule 錯誤 → `400`

這個規則的中文意義是：

> 要把「資料格式錯」和「業務規則不允許」分開，不然 API 行為會很混亂。

# 6. SaaS 必要功能（SaaS-Critical Functions）

這一層不是單純業務功能，而是 SaaS 化一定要先考慮的能力。

## 6.1 Tenant Isolation
- 所有 Tenant Data 寫入都必須強制覆寫 `company_id = current_company_id`
- 所有 Tenant Data 查詢都必須 `WHERE company_id = current_company_id`
- 不可做 application layer filter
- 不可信任 request body / querystring 帶進來的 company_id

## 6.2 Membership 關係
- user 與 company 的 membership
- `UNIQUE (user_id, company_id)`
- 公司登入名稱 `UNIQUE (company_id, login_username)`

## 6.3 平台資料與租戶資料分離
- Platform Data 不含 `company_id`
- Platform Data 不參與 company restore
- Tenant Data 必須完整受 company 綁定

## 6.4 權限模型
- 平台角色
- 公司角色
- 角色需能支援 SaaS 管理、客服支援、公司內操作

## 6.5 可恢復性與可治理性
- company 級資料 restore
- audit trail
- retention 規則
- 平台治理操作的可追溯性

## 6.6 擴充性
- 新模組應遵守同一套 tenant / scope / feature gate 規則
- 新功能應可被模組化吸收，而非任意長到核心模組

## 6.7 單租戶備份 / 還原前置檢查（來自 SA1.7 補充）
這一段是 SA1.7 裡很值得保留的內容，SA2.1 只有講方向，沒有講得這麼細。

### Company Consistency Check
- 備份資料若含 `company_id`，必須一致
- 若資料內混入其他 company，不能默默接受

### FK Closure Check
- 備份集裡若有外鍵引用，對應資料也要一起在備份集內
- 不能 restore 後指到別家公司資料

中文意思是：

> 備份 / 還原不只是「有 company_id 就好」，還要保證資料集合本身是乾淨且閉合的。

## 6.8 租戶資料模型設計原則（來自 SA1.7 補充）
這也是 SA1.7 裡非常有價值、但 SA2.1 沒展開的一段。

### 主鍵設計
- Tenant Data 建議使用 UUID
- 不要依賴 auto-increment INT 當成跨環境可搬移的主鍵

### 索引設計
- 所有 Tenant Data 都要對 `company_id` 建 index
- 目的是讓 tenant filter、單租戶匯出、restore 前檢查都能有效率

### restore-friendly 設計
- 資料模型設計要考慮未來單租戶 restore
- 不能把跨租戶依賴藏在資料模型裡

中文意思是：

> 不是只有 API 要支援 SaaS，連資料模型一開始就要為 restore 與資料搬移做準備。

# 7. 業務模組功能（Business Module Functions）

以下是 SA2.1 藍圖中的模組與其應有功能。

## 7.1 `tenants`
- company CRUD
- company active / inactive 管理
- members 管理
- onboarding
- entitlements 管理
- company source of truth

## 7.2 `auth`
- login
- password verification
- JWT issuance
- membership lookup
- login identity validation

## 7.3 `attendance`
- punch in / punch out
- break out / break in
- attendance session lifecycle
- duration / work hour calculation
- attendance status / history query
- attendance semantics owner
- `PENDING_APPROVAL` 不參與推導
- 必須是 `APPROVED IN` 才成立出勤

## 7.4 `locations`
- allowed locations 管理
- GPS / geofence 規則
- location policy 驗證
- 與 attendance punch 流程整合
- 後端 authoritative enforcement
- 不可信任前端傳來的 `location_id`

## 7.5 `approvals`
- approval 流程定義
- approval 決策狀態
- 可支援多種需要審批的業務流

## 7.6 `notifications`
- 事件訂閱
- 事件轉通知資料
- 通知查詢

## 7.7 `vehicles`
- 車輛主檔
- 車輛狀態
- 車輛與業務流程整合

## 7.8 `dispatch`
- 派工任務
- 派工流程
- 派工與人員 / 車輛 / 地點整合
- 預設只做較基礎的流程等級（SA1.7 提過 level 0 / 1 概念）
- 未完成 `APPROVED IN` 不可開始用車
- 支援 AutoClose 類型規則

## 7.9 `leave`
- 請假申請
- 請假查詢
- 請假審批
- 請假生命週期
- **只管理請假流程，不直接改 attendance 核心語意**

## 7.10 `accrual`
- 假別 / 點數 / 時數累積
- accrual ledger
- 假勤累積規則
- **只管理 ledger / 額度，不直接改 attendance 核心語意**

## 7.11 `reporting`
- 只讀報表
- 聚合查詢
- 不作為 semantic owner
- 不直接改寫業務核心資料
- 不做任何規則或狀態變更

## 7.12 trusted device / site pairing（來自 SA1.7 補充）
這塊在 SA2.1 沒明寫，但 SA1.7 有定義，而且如果你未來還會碰裝置綁定，它值得保留成基線能力。

應有功能包含：
- pairing code 僅用於裝置綁定
- pairing code 應為 short-lived、one-time
- scope 應綁 `company_id + site_id`
- 配對成功後，可形成某種 site match / trusted device 基礎狀態

中文意思是：

> 配對碼不是每天打卡憑證，而是裝置綁定工具，不能把它直接當成出勤合法性的唯一依據。

# 8. 尚未落地但藍圖有的功能（Blueprint Exists, Not Necessarily Implemented Yet）

這一段很重要，因為它是你後面做「現況比對」的依據。

## 8.1 明確在 SA2.1 / SA1.7 藍圖中出現，但未必已完整落地的模組
- `locations`
- `approvals`
- `vehicles`
- `dispatch`
- `accrual`
- `reporting`
- trusted device / site pairing 相關能力
- 單租戶 backup / restore 的完整前置檢查流程

## 8.2 這些功能目前的可能狀態
之後要做現況比對時，會出現 3 種情況：

### 類型 A：尚未開始做
- 模組存在於藍圖
- 現況程式尚未真正形成

### 類型 B：已被內嵌到其他模組
例如：
- `locations` 可能被先放進 `attendance`
- `reporting` 可能先掛在 `attendance` 子域
- `approvals` 可能散在 `leave` 或其他流程內

### 類型 C：已被現況設計替代
例如：
- 原始藍圖沒有很成熟的 `schedule` 模組，但現況已演進出獨立 `schedule`

這些不是現在就下判斷，而是後面做「現況對照」時再分析。

## 8.3 SA1.7 補進來、但 SA2.1 較少明寫的測試基線
下面這些雖然比較像驗證項，但其實也代表「功能必須能被驗證存在」：

### Tenant Isolation 測試能力
- A 公司不能讀 B 公司資料
- body 帶錯 company_id 也不能寫進別家公司
- 無 membership / 無 assignment 應被拒絕

### Backup / Restore 測試能力
- 匯出 company A 時不得混入 company B
- 還原到 company A 後不得看到 company B 資料
- 備份檔混入其他 company_id 時必須 fail fast

### Attendance 核心回歸能力
- `PENDING_APPROVAL` 不參與推導
- approval 後需重算
- 日結缺卡 / 可能缺卡邏輯正確

中文意思是：

> 這些不只是 QA 項目，它們其實在定義系統「必須具備且可驗證」的核心能力。

# 9. 這份功能清單如何用來建立 SDD

你之後應該這樣使用：

## Step 1：先從這份功能清單選一塊
例如：
- 多公司 / `company_id` 隔離
- auth
- tenants
- attendance
- reporting

## Step 2：再問 SDD 問題
對每一塊問：
- 這功能屬於哪個模組？
- 誰是 semantic owner？
- 誰只讀？
- query / write 如何隔離？
- 會依賴哪些模組？
- 不應該由誰負責？

## Step 3：再做現況比對
最後才問：
- 現在有沒有做？
- 做在哪裡？
- 有沒有偏離藍圖？
- 要回歸藍圖、承認現況、還是另立新模組？

# 10. 這次比對 SA1.7 後補上的重點摘要

如果只講結論，這次我認為 **SA2.1 容易漏掉、但 SA1.7 值得補進基線** 的重點有：

1. **Tenant Isolation 不只是原則，還要有工程保證手段**  
   例如 base repo、query helper、middleware、RLS。

2. **Backup / Restore 需要前置檢查**  
   包含 company consistency check 與 FK closure check。

3. **Tenant Data 的資料模型要為 restore 設計**  
   包含 UUID 主鍵、`company_id` index、避免跨租戶隱性依賴。

4. **API error handling 要分清楚 400 與 422**  
   schema error 與 business rule error 不能混在一起。

5. **attendance / leave / accrual / reporting / dispatch 邊界語意要再講清楚**  
   尤其是 attendance semantic owner 不可被其他模組偷偷改壞。

6. **trusted device / site pairing 是舊藍圖能力，之後要決定保留或淘汰**  
   但在做現況比對前，不應該直接遺忘它。

7. **必跑測試本身也是功能基線的一部分**  
   因為它代表哪些能力被視為不可破壞。
