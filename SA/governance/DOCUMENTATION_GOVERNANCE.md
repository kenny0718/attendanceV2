# 文件治理規範

## 1. 目的

解決以下問題：
- 文件分散
- AI 僅修改程式、不回寫文件
- 模組邊界逐漸重疊
- 後期維護時無法快速判斷單一功能應放在哪裡
- 長文件在修改時發生截斷、縮水或整檔覆寫事故
- 缺少一份可快速查詢「做過哪些事」的總表

本文件定義未來所有開發都必須遵守的回寫規則與長文件安全修改規則。

---

## 2. 單一權威原則

本專案正式文件唯一入口為：
- `/opt/attendance-system/SA`

以下路徑不再作為正式文件區：
- `/opt/attendance-system/docs`
- 模組內零散暫存說明檔
- 工作票產生但未整併的臨時 markdown

---

## 3. 每次開發完成後必做事項

### 3.1 若修改系統架構或跨模組流程
必須更新：
- `SA/architecture/SYSTEM_SDD.md`
- `SA/architecture/MODULE_BOUNDARY_MATRIX.md`

### 3.2 若修改單一模組
必須更新：
- 對應 `SA/modules/<module>.md`

### 3.3 若新增規範、開發流程、回寫要求
必須更新：
- `SA/governance/DOCUMENTATION_GOVERNANCE.md`

### 3.4 每次事項都必須登錄總表
必須更新：
- `SA/CHANGELOG.md`

規則：
- 每次開發、規劃、IA 調整、欄位規格變更、權限調整、API 契約變更、模組責任變更完成後，都必須新增一筆總表紀錄
- 總表只記摘要與索引，不重複貼完整細節
- 細節仍應寫回對應正式文件（`SA/modules/*.md`、`SA/architecture/*.md`、`SA/governance/*.md`）
- 若無總表紀錄，視為正式回寫未完成

---

## 4. 回寫最低標準

每次功能完成，至少補上：

1. 功能目的
2. 影響模組
3. API / service / repo / model 的改動點
4. 是否影響權限、租戶隔離、feature gate、事件流
5. 是否造成模組邊界變動
6. 已知限制與後續待辦
7. 對應總表紀錄位置（`SA/CHANGELOG.md`）

---

## 5. 模組邊界管理規則

若某段邏輯出現以下狀況，必須先更新 SDD 再繼續實作：

- 同一功能在兩個模組都開始出現
- 一個模組直接讀寫另一模組資料
- API 層承擔過多業務協調
- service 與 repo 職責混淆
- 舊流程與新流程並存但沒有退場說明

---

## 6. AI 協作規則

### AI 長文件操作口訣（強制）
- 先讀、先備份、小改動
- 看到 `+1 -很多`、大小縮水、行數異常下降就停
- 出現 `0KB` / 空檔 / diff 異常：先停、找來源、先恢復再重試

詳細規則一律依 `## 7 SDD / Markdown 長文件安全修改規則（正式）` 執行。

補充要求：修改 `SA/*.md` 正式文件時，AI 必須先自行用安全 patch 流程完成一次驗證；未通過驗證前，不得正式寫入治理文件或其他 `SA` 正式文件。

未來不論是 AI 還是人工開發，都應遵守：

1. 先讀 `SA/` 再改程式
2. 程式改完必須回寫 `SA/`
3. 若無法確認邊界，先補 architecture 文件
4. 不再把新設計寫回舊 `docs/`
5. 每次事項完成後，必須同步更新 `SA/CHANGELOG.md`

---

## 7. SDD / Markdown 長文件安全修改規則（正式）

本節為正式治理規則，之後修改長文件一律照此執行。

### 7.1 適用範圍
以下任一條件成立，即視為長文件或高風險文件：

- `SA` 正式文件一律視為高風險，不以大小或行數作為豁免條件
- 其中包含：`SA/modules/`、`SA/architecture/`、`SA/governance/`、`SA/SDD_PROGRESS_TRACKER.md`、`SA/CHANGELOG.md`
- 其他非 `SA` 文件，只要檔案大小超過 `4KB`
- 其他非 `SA` 文件，只要檔案行數超過 `150` 行
- 曾發生過截斷、0 byte、異常縮水、內容覆蓋事故的文件

### 7.2 核心原則
對長文件的修改，必須遵守以下原則：

1. **禁止無必要整檔覆寫**
   - 以局部段落替換為預設策略
   - 不可為了改單一章節而重寫整份文件
   - 不可先清空再重建

2. **必須先讀原文再修改**
   - 先確認目標章節
   - 先確認上下文仍存在
   - 不可憑記憶、對話內容或推測版本重建文件

3. **修改前必須先建立時間戳備份**
   - 備份檔名必須帶到秒級時間
   - 建議格式：`<filename>.bak-YYYYMMDD-HHMMSS`
   - 同一天多次修改不得共用同一個只有日期的備份名

4. **修改後必須做完整性驗證**
   - 檔案不可為空
   - 檔案大小不可異常縮水
   - 行數不可異常下降
   - 目標章節前後文必須仍存在
   - 若只改單一章節，必須確認其他章節未被意外吃掉

5. **檔案異常時禁止續寫**
   - 若出現 0 byte、截斷、結構缺失或讀取結果異常
   - 必須先停止
   - 必須先回復備份或 restore
   - 不可直接在異常檔案上繼續 patch

### 7.3 標準修改流程（SOP）
每次修改長文件時，固定依下列順序進行：

1. 判定是否屬於長文件 / 高風險文件
2. 讀取原文並定位要修改的章節
3. 建立時間戳備份
4. 採用局部 patch / 段落替換
5. 先檢查本次修改是否符合預期 diff 規模
6. 修改後重新讀取目標段落與相鄰章節
7. 驗證檔案大小、行數與完整性
8. 最後才更新 Change Log / Datetime

### 7.4 Diff 異常即停止規則
若本次任務原本只應修改小區塊，但實際變更出現以下任一情況，必須立即停止，不得繼續寫入：

- 預期只改 `1~5` 行，實際卻出現大量刪除
- diff 呈現類似 `+1 -很多`、`+3 -幾十`、`+5 -上百` 這種不成比例變更
- 目標章節以外內容被一起刪除
- 檔案大小明顯縮水
- 行數異常下降
- 讀回結果與原本章節結構不一致

處理原則：
- 立即停止，不再追加寫入
- 先檢查是否命中錯誤替換範圍
- 先檢查檔案是否已異常或遭截斷
- 必要時先回復備份，再重新進行最小範圍 patch

### 7.5 禁止事項
以下行為視為違反治理規則：

- 為了改一小段而整份重寫長文件
- 在未讀原文情況下直接覆蓋文件
- 用對話內容、記憶內容、推測內容重建正式文件
- 修改後不驗證檔案大小 / 行數 / 相鄰章節
- 發現文件異常仍繼續寫入
- 只留日期備份，不留時間
- 已出現異常 diff 訊號仍繼續硬寫

### 7.6 事故處置流程（0KB / 空檔 / diff 異常）
若發生 `0KB`、空檔、讀取結果異常、或出現 `+1 -很多` 這類 diff 異常，必須依下列三步驟處理，以減少異常排除時間：

1. **先停止寫入**
   - 不再追加 patch
   - 不再嘗試第二次覆蓋
   - 不可直接在異常檔案上補內容

2. **先確認異常類型與可恢復來源**
   - 檢查是否為 `0 byte`、內容截斷、章節消失、或替換範圍命中錯誤
   - 優先找時間戳備份、原始檔、或其他可靠 restore 來源
   - 未找到可信來源前，不可憑記憶重建正式文件

3. **先恢復，再做最小範圍驗證與重試**
   - 先把檔案恢復到可讀狀態
   - 驗證檔案大小、行數、目標章節與相鄰章節完整
   - 確認恢復正常後，才允許重新進行最小範圍 patch

目標：**先把事故侷限住，再恢復，再繼續**，避免把一次小修改擴大成長文件重建事故。

### 7.7 例外條件
只有在以下情況，才可考慮整檔重寫：

- 檔案本身已確認異常且已有可靠來源可完整回復
- 使用者明確要求整份重整 / 全面改寫
- 已先完成備份，且可立即驗證前後版本差異

即使符合例外條件，也仍需：
- 先備份
- 先確認來源可信
- 重寫後重新驗證完整性

## 8. Change Log / 修改紀錄規則

### 8.1 時間格式規則
未來所有正式文件的 Change Log，不再只寫 `Date:`。

一律改為：
- `Datetime: YYYY-MM-DD HH:MM:SS +08:00`

例如：
- `Datetime: 2026-04-08 15:32:10 +08:00`

### 8.2 最低欄位
若文件有 Change Log，至少應包含：

- `Datetime:`
- `Status:`
- `Summary:`

若有下一步，建議補：
- `Next:`

### 8.3 同日多次修改
同一天若有多次修改，必須以時間區分，不可只保留日期。

### 8.4 SA 總表制度
`SA/CHANGELOG.md` 為正式總表索引。

用途：
- 統一查詢「做過哪些事」
- 用摘要方式記錄每次規劃、文件回寫、code 修改與治理調整
- 作為各細節文件的入口索引

要求：
- 每次事項完成後，都必須新增一筆紀錄
- 總表只記摘要，不重複貼完整規格內容
- 細節應回寫至對應正式文件
- 若事項已完成但未登錄總表，視為回寫未完成

---

## 9. 棄用策略

- 舊 `docs/` 已完成退場，不再保留於專案根目錄
- 歷史上仍值得追溯的內容，應保留於 `SA/legacy-import/`
- 若某些舊文件不再需要追溯價值，則不必搬入 `SA/legacy-import/`，可直接刪除
- 新決策、新規範、新模組說明只允許寫在 `SA/`
- 不可為了保留而保留；歷史區僅保存對追溯、比對、治理仍有價值的資料
